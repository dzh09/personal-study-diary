外包实现不等于外包架构责任

概念 · 科技 · 入 2026-11-02

全篇核心判断：采购的是实现效率，不是信任决策。能不能托付看四条：是不是每笔交易都过它、断网还能不能用、能不能只给必要字段、藏起来之后谁还敢负责。

判断：提供商的 verifyCredential() 能跑通，只说明 API 可用；企业仍须回答六个问题——

  1. 凭证存在哪？设备密钥如何保护？
  2. 谁管签发方信任锚？证书如何验证与轮换？
  3. 凭证有效性与撤销怎么处理，尤其验证方离线时？
  4. 哪些属性会被披露？能否强制执行数据最小化？
  5. 提供商收集哪些遥测？出示事件能否关联到具体用户？
  6. 提供商不可用时怎么办？能否不改架构就换供应商？

为什么这些不能外包：它们属于信任边界，一旦出错是企业的责任，不是 SDK 的 bug。

迁移：换成任何第三方能力都成立——支付、风控、地图、大模型 API。判断句式：「这件事出了事，谁负责？如果是我们，那就不能只看 API 文档。」

  • 四条判据（原各一张卡，现并入本卡）：
  • 架构级单点：单点不是「经常挂」，而是「每笔交易都必须经过它」；99.99% 可用性 × 每笔依赖，仍是单点。
  • 离线能力：演示全程联网，就不能证明有离线能力；九类必测——无网出示、无网验证、缓存信任材料、过期凭证、过期撤销信息、恢复网络、重连同步、时钟异常等。
  • 选择性披露：同一凭证可只给一个布尔值（age_over_21），配套是数据最小化与零追踪；缺一条，技术就成监控工具。
  • 抽象边界：该藏的（CBOR、APDU、密码学库、NFC 会话）与必露的（信任锚、签发方、验证结果、已披露属性、撤销状态、对提供商的依赖、离线能力、安全边界、故障条件）分两张清单；标准不是难易，是「藏起来之后谁还敢负责」。
  • 投产前五问：信任边界在哪、数据给了谁、断网能不能用、哪个环节断了全停、换供应商要多久。不必懂密码学也能问，每问都能落成一张表。
